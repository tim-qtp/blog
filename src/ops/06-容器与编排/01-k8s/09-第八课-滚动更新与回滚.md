# 第八课：Deployment 滚动更新与回滚

## 这节课只解决一个问题

线上有三个正在运行的旧版本 Pod，怎样升级镜像，同时避免一次性把三个旧 Pod 全部停掉？如果新版本有问题，又怎样恢复？

Deployment 默认采用滚动更新：

```text
逐步创建新版本 Pod
逐步删除旧版本 Pod
直到全部替换完成
```

如果发布失败，可以回滚到上一次版本。

## 一、为什么不能先删光再重建

当前有三个旧版本 Pod：

```text
旧 Pod A
旧 Pod B
旧 Pod C
```

最直接但风险很高的更新方式是：

```text
同时删除 A、B、C
        ↓
再创建三个新 Pod
```

中间会出现没有 Pod 提供服务的时间。

滚动更新的思路是逐批替换：

```text
第 1 步：旧、旧、旧
第 2 步：新、旧、旧
第 3 步：新、新、旧
第 4 步：新、新、新
```

这张图只表达核心思想。实际过程中 Kubernetes 可能短暂多创建一个 Pod，替换顺序也不保证与图完全一致。

## 二、先部署旧版本

实验文件：`labs/06-滚动更新/01-nginx-deployment-v1.yaml`

其中最重要的两处是：

```yaml
replicas: 3
```

表示维持三个 Pod；

```yaml
image: nginx:1.26
```

表示初始镜像版本是 Nginx 1.26。

进入课程目录：

```bash
cd /Users/qintianpeng/2026/code/k8s
```

创建 Deployment：

```bash
kubectl apply -f labs/06-滚动更新/01-nginx-deployment-v1.yaml
```

等待部署完成：

```bash
kubectl rollout status deployment/qingyun-mall-web
```

看到下面这行表示三个旧版本 Pod 都已准备好：

```text
deployment "qingyun-mall-web" successfully rolled out
```

查看 Pod：

```bash
kubectl get pods -l 'app=qingyun-mall,tier=frontend'
```

应该有三个 `1/1 Running`。

## 三、确认当前使用的镜像

执行：

```bash
kubectl get deployment qingyun-mall-web \
  -o jsonpath='{.spec.template.spec.containers[0].image}{"\n"}'
```

输出：

```text
nginx:1.26
```

这条命令虽然较长，但目的很简单：从 Deployment 的 Pod 模板中取出容器镜像。

## 四、准备观察更新过程

在第一个终端执行：

```bash
kubectl get pods -l 'app=qingyun-mall,tier=frontend' -w
```

保持这个终端运行。

## 五、把镜像升级到 Nginx 1.27

打开第二个终端，执行：

```bash
kubectl set image deployment/qingyun-mall-web nginx=nginx:1.27
```

拆开理解：

```text
kubectl set image             修改容器镜像
deployment/qingyun-mall-web    操作这个 Deployment
nginx=nginx:1.27              名为 nginx 的容器改用 nginx:1.27
```

注意等号左边的 `nginx` 是 YAML 中的容器名称：

```yaml
containers:
  - name: nginx
```

等号右边的 `nginx:1.27` 是新镜像。

## 六、观察滚动替换

回到第一个终端，你会看到：

- 新 Pod 出现并进入 `ContainerCreating`；
- 新 Pod 变为 `Running`；
- 旧 Pod 进入 `Terminating`；
- 最终重新稳定为三个 Running Pod。

完成后按 `Control + C`。

等待发布完成：

```bash
kubectl rollout status deployment/qingyun-mall-web
```

再查询镜像：

```bash
kubectl get deployment qingyun-mall-web \
  -o jsonpath='{.spec.template.spec.containers[0].image}{"\n"}'
```

现在应输出：

```text
nginx:1.27
```

## 七、为什么修改镜像会创建新 Pod

Deployment 的 `template` 是 Pod 模板。镜像正是模板的一部分：

```text
旧模板：image = nginx:1.26
新模板：image = nginx:1.27
```

已经运行的 Pod 不会在原地把镜像换掉。Deployment 会根据新模板创建新 Pod，并逐步删除旧 Pod。

所以升级本质上是：

```text
替换 Pod，而不是进入旧容器现场改程序
```

## 八、查看发布历史

执行：

```bash
kubectl rollout history deployment/qingyun-mall-web
```

输出会列出 `REVISION`，也就是发布修订编号，例如：

```text
REVISION  CHANGE-CAUSE
1         <none>
2         <none>
```

可以先理解为：

```text
revision 1：最初的 Pod 模板
revision 2：修改镜像后的 Pod 模板
```

`CHANGE-CAUSE` 为空不影响本课实验。它只是说明我们没有额外记录发布说明。

## 九、故意发布一个不存在的版本

执行：

```bash
kubectl set image deployment/qingyun-mall-web \
  nginx=nginx:lesson-version-does-not-exist
```

等待发布状态，但设置 20 秒超时：

```bash
kubectl rollout status deployment/qingyun-mall-web --timeout=20s
```

这次预期不会显示成功，而会在超时后返回错误。因为新 Pod 无法拉取不存在的镜像。

查看 Pod：

```bash
kubectl get pods -l 'app=qingyun-mall,tier=frontend'
```

你会看到两类 Pod：

- 旧版本 Pod 仍然 Running；
- 新版本 Pod 显示 `ErrImagePull` 或 `ImagePullBackOff`。

这体现了滚动更新的价值：新版本没有准备好时，Deployment 通常不会立刻删光全部可用旧 Pod。

## 十、确认失败原因

先找出状态异常的新 Pod：

```bash
kubectl get pods -l 'app=qingyun-mall,tier=frontend'
```

复制异常 Pod 的完整名称，然后执行：

```bash
kubectl describe pod <异常Pod名称>
```

查看底部 Events，应能发现：

```text
Failed to pull image
not found
ImagePullBackOff
```

这与第五课的错误镜像故障相同，只是这次发生在发布新版本期间。

## 十一、回滚到上一次版本

确认失败后，执行：

```bash
kubectl rollout undo deployment/qingyun-mall-web
```

`undo` 表示撤销最近一次 Pod 模板变更，恢复到上一个修订版本。

等待回滚完成：

```bash
kubectl rollout status deployment/qingyun-mall-web
```

查询镜像：

```bash
kubectl get deployment qingyun-mall-web \
  -o jsonpath='{.spec.template.spec.containers[0].image}{"\n"}'
```

应恢复为：

```text
nginx:1.27
```

再看 Pod：

```bash
kubectl get pods -l 'app=qingyun-mall,tier=frontend'
```

最终应重新稳定为三个 `1/1 Running` Pod。

## 十二、回滚不是恢复原来的 Pod

与自动恢复一样，回滚恢复的是以前的 Pod 模板，而不是把被删除的旧 Pod 原地找回来。

```text
恢复旧模板
   ↓
根据旧模板创建替代 Pod
   ↓
删除失败版本 Pod
```

所以回滚后 Pod 名称仍可能发生变化。

## 十三、本地 YAML 又与集群不一致了

实验 YAML 仍写着：

```yaml
image: nginx:1.26
```

但是经过升级和回滚后，集群当前是：

```text
nginx:1.27
```

因为 `kubectl set image` 和 `kubectl rollout undo` 修改的是集群对象，不会自动改写本地文件。

如果此时重新 apply 初始 YAML：

```bash
kubectl apply -f labs/06-滚动更新/01-nginx-deployment-v1.yaml
```

集群会再次按照文件回到 `nginx:1.26`。

本课为了清楚观察过程使用命令修改。实际项目中应把最终镜像版本写回受 Git 管理的部署配置，保证文件记录与集群期望一致。

## 十四、清理实验

执行：

```bash
kubectl delete -f labs/06-滚动更新/01-nginx-deployment-v1.yaml
```

虽然文件中写的是旧镜像，但删除依据主要是对象类型和名称，所以仍会删除当前名为 `qingyun-mall-web` 的 Deployment。

确认：

```bash
kubectl get deployment,replicaset,pod -l 'app=qingyun-mall,tier=frontend'
```

下层资源可能短暂显示 `Terminating`，稍等后再次查询，最终应全部消失。

## 十五、问题与直接回答

### 滚动更新会一次性删除所有旧 Pod 吗？

通常不会。Deployment 会逐步创建新 Pod、删除旧 Pod，尽量在更新期间保留可用副本。

### 更新镜像是在原容器里替换程序吗？

不是。Pod 模板变化后，Deployment 创建使用新镜像的新 Pod，并删除旧 Pod。

### `rollout status` 成功代表业务功能一定正确吗？

不代表。它表示 Deployment 的发布状态达到预期。业务接口和页面仍需要实际请求验证，后面学习健康检查后还会改善判断能力。

### 新镜像拉取失败，为什么旧 Pod 还在？

因为新 Pod 尚未可用，滚动更新策略不会直接把所有旧的可用副本删除。

### `rollout undo` 恢复的是原 Pod 吗？

不是。它恢复上一个 Pod 模板，再根据该模板创建替代 Pod。

### 为什么回滚后本地 YAML 没变？

因为回滚操作修改的是集群中的 Deployment，不会自动编辑本地文件。

## 本课只记住五句话

1. 滚动更新通过逐步创建新 Pod、删除旧 Pod 完成版本替换。
2. 修改 Pod 模板不会原地修改旧 Pod，而会创建替代 Pod。
3. `rollout status` 查看发布是否完成，`rollout history` 查看修订历史。
4. 新版本失败后，可以用 `rollout undo` 恢复上一个 Pod 模板。
5. 发布或回滚后仍要让本地配置与集群最终版本保持一致。
